# 前端技术视野·每日简报 · 2026-10-19

## 🔥 1. 今日技术热点：TC39 Signals 提案把「细粒度响应式」拉到语言层

**是什么**：TC39 的 `Signal` 提案（proposal-signals，由 Rob Eisenberg、Daniel Ehrenberg 等推动，目前处于 Stage 1，具体阶段请以 TC39 议程为准 —— **待验证**）打算把 Solid / Vue / Preact Signals / Angular Signals 共用的那套「值 + 依赖追踪 + 派生 + 副作用」原语标准化成 `Signal.State` / `Signal.Computed` / `Signal.subtle.Watcher` 三件套。

**它解决什么旧痛点**：
- 各框架自己实现一遍响应式，心智模型互不兼容，跨框架复用业务逻辑几乎做不到。
- `useState` + 依赖数组这种粗粒度模型需要「比较整棵子树」才能决定更新范围，和真正的「谁依赖谁」解耦得不彻底。
- 浏览器平台 API（Observable、EventTarget）表达的是「事件流」，不是「可读取的最新值」，二者并非一回事。

**底层原理 / 关键设计**：
1. **拉取式求值 + 推送式失效**：`Computed` 不在源变化时立刻重算，而是把下游标记为 dirty，等有人 `get()` 时再按依赖图回溯；这避免了「无人消费也在算」的浪费。
2. **动态依赖收集**：`Computed` 的 getter 执行时，当前 Watcher 入栈，被读取的 `Signal.State` 把自己登记到栈顶，执行完再出栈 —— 和 Vue 3 reactivity 完全同构。
3. **副作用隔离**：提案把「什么时候执行副作用」留给宿主（框架/调度器），只在 `Signal.subtle.Watcher` 上暴露通知时机，防止把 microtask/raf 的策略写死进语言。

**对我日常工作的影响**：短期内不会直接写 `new Signal.State(0)`，但三件事值得现在做：① 新项目选型时倾向于那些 Signals-first 的框架（Solid / Preact / Qwik / Vue 3.4+），迁移成本会比 hooks 系低；② React 内部也在跟进（React Compiler + `useSyncExternalStore` 组合），别再写「用 useState 存派生值」这种反模式；③ 自己写状态库时，`Watcher.notify` 和 `Computed` 的 lazy 语义是标准答案，别再发明 subscribe 回调满天飞的轮子。

## 📘 2. 一个值得掌握的概念：浏览器合成层（Compositor Layers）

**是什么**：浏览器把页面渲染流水线切成 Parse → Style → Layout → Paint → **Composite** 五段。Composite 阶段，GPU 把若干「层（layer）」按 z 轴叠起来；每一层本质是一张位图纹理，可以独立 transform/opacity，不触发前面任何一步。

**为什么需要**：Layout 和 Paint 跑在主线程、要走 CPU，一旦整页重排就直接丢帧。合成层让「只是动画位置/透明度」的变化绕开主线程，直接由合成器线程把纹理搬到新位置 —— 这就是「60fps transform 丝滑，top/left 卡顿」的根因。

**怎么实现（Chromium 心智模型）**：
- **提升为层的触发条件**：3D transform（含 `translateZ(0)`）、`will-change: transform/opacity`、`<video>`/`<canvas>`、`position: fixed` 在滚动容器中、`backdrop-filter`、`filter`、根据层叠上下文判定的 overlap 等。
- **动画走合成器**：只有 `transform`、`opacity`、`filter`（部分）、`backdrop-filter` 能被 compositor 直接处理；`top/left/width/background-color` 必然回到主线程 Paint。
- **代价**：每层单独一张纹理，4 字节/像素；一个 1920×1080 的全屏层 ≈ 8MB 显存，层爆炸会把低端设备拖死。

**边界与误区**：
1. `will-change` 不是银弹，常驻会浪费内存，用完要撤销（动画结束移除 class）。
2. `translateZ(0)` 这个 hack 在新版 Chrome 已经不是提层的充分条件，别照抄 2016 年的文章。
3. 合成层数量请用 DevTools → **Rendering → Layer borders** 或 Performance 面板的 Layers 轨道实测，而不是靠猜。

## 🧩 3. 深度面试题：封装一个「可取消 + 超时 + 指数退避重试」的 fetch

**题干**：请实现 `robustFetch(input, init?)`，支持三个额外选项：`timeoutMs`（单次请求超时）、`retries`（最大重试次数）、`signal`（外部主动取消）。要求：外部取消必须立刻生效、超时和外部取消要能并存、只对网络错误 / 5xx 重试，4xx 不重试。

**三个追问**：
1. 外部传入的 `signal` 和内部为超时创建的 `AbortController` 如何「组合」成一个？能否在不手动监听事件的前提下做到？
2. 为什么重试要用「指数退避 + 抖动（jitter）」？没有 jitter 会发生什么？
3. 如果业务要求「取消时正在进行的那次请求要被标记为 `AbortError`，而不是被当作网络错误再触发一次重试」，代码里哪一行最容易踩坑？

**参考答案**：

```ts
export async function robustFetch(
  input: RequestInfo,
  init: RequestInit & { timeoutMs?: number; retries?: number } = {}
): Promise<Response> {
  const { timeoutMs = 8000, retries = 2, signal: outer, ...rest } = init;

  for (let attempt = 0; ; attempt++) {
    // AbortSignal.any 是 Baseline 2024+，不可用时退回手动 forward
    const timer = AbortSignal.timeout(timeoutMs);
    const composed = outer
      ? AbortSignal.any([outer, timer])
      : timer;

    try {
      const res = await fetch(input, { ...rest, signal: composed });
      if (res.status >= 500 && attempt < retries) throw new Error('5xx');
      return res; // 2xx / 3xx / 4xx 都直接返回，交给调用方判断
    } catch (err: any) {
      // 外部取消立刻冒泡，绝不重试
      if (outer?.aborted) throw new DOMException('Aborted', 'AbortError');
      if (attempt >= retries) throw err;
      const backoff = 2 ** attempt * 200 + Math.random() * 100; // jitter
      await new Promise(r => setTimeout(r, backoff));
    }
  }
}
```

**考察点**：`AbortController`/`AbortSignal.any`/`AbortSignal.timeout` 的组合、Promise 控制流、幂等性与副作用边界、重试策略（指数退避 + 抖动防「惊群」）、错误分类（可重试 vs. 不可重试）。

## 🛠️ 4. 新 API 速览：Iterator Helpers（迭代器辅助方法）

**是什么**：TC39 把 `.map / .filter / .take / .drop / .flatMap / .reduce / .toArray` 直接挂到了 `Iterator.prototype` 上，让任何迭代器（含 generator）都能链式懒计算。Chrome 122+ / Node 22+ 已原生支持（**具体版本以 MDN Baseline 为准，待验证**）。

**解决什么问题**：以前要「拿 generator 的前 10 个」必须手写 `for...of + break`，或者先 `[...gen]` 把无限序列展开 —— 要么丑，要么直接 OOM。

**和已有方案对比**：

| 场景 | 数组方法 | Iterator Helpers | RxJS |
| --- | --- | --- | --- |
| 数据模型 | 立刻物化全部元素 | 懒拉取，按需求值 | 推送式事件流 |
| 内存占用 | O(n) 全量 | O(1) 中间状态 | O(1) 中间状态 |
| 无限序列 | ❌ 直接爆栈 | ✅ 配合 `take` 天然安全 | ✅ 原生支持 |
| 异步 | ❌ | 配套 `AsyncIterator.prototype` | ✅ 核心能力 |
| 心智成本 | 低 | 低（和 Array API 对齐） | 高 |

**现阶段建议**：**立刻学**。它和 async iterator、`ReadableStream.from()` 一起，正在成为前端处理「流式数据」的新共识；替代掉项目里一半的 `lodash/fp` 用法并不夸张。

## 📂 5. 源码阅读推荐：koa-compose（洋葱模型，核心仅 15 行）

**仓库 / 文件**：[`koajs/compose`](https://github.com/koajs/compose) → `index.js`，导出函数就一个 `compose(middleware)`。

**核心思路**（<200 字）：`compose` 把中间件数组压成一个 `(context, next) => Promise`。调用时从索引 0 开始递归：当前中间件拿到的 `next` 其实是「调用索引 i+1 的中间件」的一个闭包。中间件里 `await next()` 会把控制权交给下一层，所有下层执行完后 Promise resolve，再回到当前层执行后置逻辑 —— 这就是「请求穿透进去、响应穿透出来」的洋葱。关键细节是用一个 `index` 变量防止同一个 `next` 被调用两次（否则 Promise 链会分叉）。

**三个阅读切入点**：
1. 为什么要用 `Promise.resolve(fn(context, dispatch.bind(null, i + 1)))` 而不是直接 `fn(...)`？抛同步异常时的行为差异在哪？
2. `if (i <= index) return Promise.reject(new Error('next() called multiple times'))` 这行如果去掉，会出现什么现实 bug？
3. 对比 Redux 的 `applyMiddleware`：同样是「串联函数」，为什么 Redux 不叫洋葱而叫「增强」？两者的「下一个」语义有什么本质差异？
