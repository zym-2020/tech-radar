## 🔥 1. 今日技术热点：Rolldown-Vite 的全量切换与「一套工具链」愿景

**是什么**
Vite 用 Rust 写的下一代打包器 Rolldown 已逐步在 Vite 7.x 中默认替代 Rollup 作为生产构建器（具体 minor 版本号待验证）。这意味着从 dev（esbuild / Rolldown 预构建）到生产 bundle，再到 SSR 代码分割，走的是同一个底层产物图。

**解决的旧痛点**
- 过去 Vite dev 用 esbuild、prod 用 Rollup，二者行为和产物不完全一致，经常出现 "dev 正常、build 崩" 的边界 bug（如 CJS/ESM interop、循环依赖处理）。
- Rollup 用 JS 实现，大型项目 build 耗时随模块数近线性增长；Rolldown 用 Rust + OXC AST，并发友好。
- esbuild 的 tree-shaking 和代码分割策略偏粗，Rolldown 补齐了 Rollup 的产物质量。

**底层原理 / 关键设计**
- 复用 OXC（Oxidation Compiler）做 parse，比 SWC/Babel 更快，AST 数据结构零拷贝。
- 保留 Rollup 的 plugin hook 协议（`resolveId` / `load` / `transform` / `renderChunk`），在 Rust 侧通过 NAPI 调用 Node 插件，成本可控。
- Module Graph 在 Rust 侧内建，依赖分析与 HMR Boundary 不再需要 JS 侧往返。

**对日常工作的影响**
- 老项目升级 Vite 7 时，需关注插件兼容：少数依赖 Rollup 内部字段的插件要观望。
- CI 的 build 时间预计能砍掉 30%~60%（视项目规模，待验证）；但 dev 冷启动差异不大，因为 Vite dev 仍是按需编译。
- 配置迁移成本几乎为零，`vite.config.ts` 大多可直接复用。

## 📘 2. 一个值得掌握的概念：ES Module 的 Live Binding（实时绑定）

**是什么**
ESM 的 `import` 不是把被导出的值"拷贝"一份过来，而是绑定到源模块里那个标识符的内存槽。源模块再次赋值，导入侧立刻看到新值。CommonJS 的 `require` 则是把 `module.exports` 的快照赋给局部变量。

**为什么需要**
ESM 的目标是让静态分析器能画出清晰的依赖图并做 tree-shaking。只有「绑定」而不是「拷贝」，才能保证循环引用（A → B → A）的情况下，后赋的值能被看到；同时也让 HMR 的热替换粒度能落到单个绑定。

**怎么实现**
规范层面：Module Record 里有 Environment Record，每个 export 都是一个 `*binding*`；import 侧创建的是 indirect binding，取值走解引用。V8 的实现中，`export let x` 会分配一个槽，`x = 1` 实际是 `*slot = 1`，所有 import 它的模块读到的都是 `*slot`。

**边界与误区**
- `export default foo` 中，`foo` 是表达式求值的结果（default binding 是只读的），再给原 `foo` 赋值不会改默认导出。这是最容易踩的坑。
- `import` 得到的绑定是**只读**的，`import { x } from './a'; x = 2` 会抛 TypeError。
- 用 `export const` 的场景，"实时性"看起来没用，因为 const 不可变；真正能观察到活性的要用 `export let`。
- 打包后被降级为 CJS 时这个语义会丢失，别写依赖 live binding 的技巧代码。

## 🧩 3. 深度面试题：手写一个最小响应式系统

**题干**
请实现 `ref` / `effect` / `computed` 三个 API，使得下面代码能正确运行：
```js
const count = ref(0)
const double = computed(() => count.value * 2)
effect(() => console.log('double:', double.value))
count.value = 1 // 控制台应打印 "double: 2"
```

**追问 1**：如何做到 `count.value = 1` 时只触发用到它的 effect，而不是全局重跑？
**追问 2**：如果一个 effect 在不同分支里访问不同的 ref，切换分支后旧的依赖如何清理？
**追问 3**：computed 的"懒求值 + 缓存失效"如何实现？两个 computed 相互依赖会不会死循环？

**参考答案（含代码片段）**
```js
let activeEffect = null
const targetMap = new WeakMap() // ref -> Set<effect>

function track(dep) {
  if (!activeEffect) return
  dep.add(activeEffect)
  activeEffect.deps.push(dep)
}
function trigger(dep) {
  // 复制一份避免在遍历中增删
  [...dep].forEach(e => e.scheduler ? e.scheduler() : e.run())
}
function cleanup(effect) {
  effect.deps.forEach(dep => dep.delete(effect))
  effect.deps.length = 0
}
function effect(fn, options = {}) {
  const e = {
    deps: [],
    scheduler: options.scheduler,
    run() {
      cleanup(e)
      activeEffect = e
      try { return fn() } finally { activeEffect = null }
    }
  }
  e.run()
  return e
}
function ref(value) {
  const dep = new Set()
  return {
    get value() { track(dep); return value },
    set value(v) { if (v !== value) { value = v; trigger(dep) } }
  }
}
function computed(getter) {
  let dirty = true, cached
  const runner = effect(getter, {
    scheduler() { if (!dirty) { dirty = true; trigger(dep) } }
  })
  const dep = new Set()
  return {
    get value() {
      if (dirty) { cached = runner.run(); dirty = false }
      track(dep)
      return cached
    }
  }
}
```

**考察点**：依赖收集与触发、WeakMap/Set 的用法、调度器（scheduler）解耦、懒求值与脏标记、effect 的依赖清理（Vue 3 的分支切换痛点）。

## 🛠️ 4. 新工具/规范/API 速览：CSS `interpolate-size: allow-keywords` + `calc-size()`

**是什么**
一组 CSS 规范（Chromium 129+ 稳定，Firefox/WebKit 跟进中，具体版本待验证），允许在 `height: 0 → height: auto` 这种"从固定值过渡到关键字值"的场景做动画，从此告别 JS 测量高度的 hack。

**解决什么问题**
手风琴/折叠面板的展开收起动画，20 年来一直靠 "`max-height` 瞎估一个大数" 或 JS 读 `scrollHeight` 再 `requestAnimationFrame`。前者动画缓动不自然，后者 SSR 不友好且闪烁。

**和已有方案对比**

| 方案 | 代码量 | 性能 | 缓动准确 | SSR/首帧 | 内容变化自适应 |
| --- | --- | --- | --- | --- | --- |
| `max-height` hack | 极少 | 好 | 否（时间轴偏差） | 好 | 差 |
| JS 读 scrollHeight | 中 | 中（触发 reflow） | 是 | 差（闪烁） | 好 |
| `grid-template-rows: 0fr → 1fr` | 少 | 好 | 是 | 好 | 好，但需额外 wrapper |
| `interpolate-size` | 极少 | 原生 | 是 | 好 | 好 |

**建议**：**立刻学，渐进增强使用**。写法：
```css
:root { interpolate-size: allow-keywords; }
details { transition: height 300ms; height: 0; overflow: clip; }
details[open] { height: auto; } /* 浏览器会把 auto "算出来" 再插值 */
```
在不支持的浏览器上会退化为"瞬间切换"，不影响可用性。

## 📂 5. 源码阅读推荐：`@vue/reactivity` 的 `effect.ts`

**仓库路径**：`vuejs/core` 仓库下的 `packages/reactivity/src/effect.ts` 与 `ref.ts`、`reactive.ts`、`baseHandlers.ts`。

**核心思路（自己的话）**
Vue 3 的响应式本质是「Proxy 拦截 + 依赖图」。`reactive(obj)` 返回一个 Proxy，`get` 时调 `track` 把当前正在运行的 `ReactiveEffect` 塞进依赖集合；`set` 时调 `trigger` 把该集合里的 effect 重跑。为了性能，每个 effect 会记录自己依赖了哪些 Set（双向绑定），重跑前先 cleanup，解决分支切换残留订阅的问题。调度器 `scheduler` 把"何时重跑"从"是否重跑"里剥离，让 Vue 的 `nextTick` / 异步批量更新成为可能。

**3 个阅读切入点**
1. `ReactiveEffect.run()` 里的 `shouldTrack` 栈是为什么要用栈结构？嵌套 effect 场景下会发生什么？
2. `trigger` 时为什么要把集合复制一份再遍历（见 `triggerEffects`）？
3. `computed` 是怎么用「两个 effect」（一个自身 runner + 外层依赖）实现"懒求值 + 可被别人追踪"的？对比我们第 3 题的实现差在哪？
