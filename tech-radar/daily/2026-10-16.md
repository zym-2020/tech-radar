## 🔥 1. 今日技术热点：CSS Anchor Positioning（CSS 锚点定位）

**是什么**
CSS Anchor Positioning 是一组新的 CSS 属性（`anchor-name`、`position-anchor`、`anchor()`、`position-area` 等），让一个 `position: absolute/fixed` 的元素可以声明式地「挂」在另一个元素上，并随之移动。Chrome 125 起已稳定（2024 年 5 月），Safari / Firefox 实现进度为「待验证」。

**解决了什么旧痛点**
过去实现 Tooltip、Popover、下拉菜单的定位，几乎必须依赖 `getBoundingClientRect` + `scroll/resize` 监听 + JS 计算边界回退，产物就是 Popper.js / Floating UI 这类库。它们带来三类问题：
1. 首次渲染存在「错位闪烁」（JS 执行晚于 Paint）。
2. 大量滚动监听影响性能，容易触发强制同步布局（layout thrash）。
3. 跨组件边界、Shadow DOM 场景下，坐标系换算复杂。

**底层原理 / 关键设计**
- `anchor-name: --btn` 把一个元素注册为锚点。
- 浮层通过 `position-anchor: --btn` + `top: anchor(bottom)` 读取锚点的具体边。
- `position-area: bottom span-right` 用「网格区域」语义声明方位，不再手写 `top/left`。
- `position-try-fallbacks`（旧名 `position-try`）用于「空间不够则换方位」的翻转策略，等价于 Floating UI 的 `flip` 中间件。
- 关键在于：定位发生在渲染引擎内部，和布局同一帧完成，无需 JS 介入，也不会被滚动打断。

**对日常工作的实际影响**
- 新项目：Tooltip / Popover / Menu 这类组件可以逐步剥离 Floating UI，减少包体积约 10–15 KB（gzip 后，待验证）。
- 已有项目：短期仍需 Floating UI 兜底 Firefox 等；但组件 API 可以提前对齐 `position-area` 的语义，为未来降级做准备。
- 面试加分点：能聊「为什么锚定要在渲染引擎做，而不是 JS 做」—— 本质是把一次「跨帧依赖」转化为「同帧 layout 结果」。

## 📘 2. 一个值得掌握的概念：CSS Containment（`contain` 属性）

**是什么**
`contain: layout | paint | size | style | content` 告诉浏览器「这个盒子内部的某些变化不会影响外部」，从而让渲染引擎可以把它当成一个独立子树去 layout / paint / 计算样式。

**为什么需要（第一性原理）**
浏览器渲染是一棵「依赖树」。默认情况下，任何一个节点的尺寸、样式变化，理论上都可能通过百分比、`:has()`、`em`、`float` 等机制影响到祖先或兄弟。所以浏览器在布局时必须「向上/向外探测」。`contain` 是开发者给引擎的一个**契约**：你可以信任我，这个边界内外解耦，不用再越界计算。

**怎么实现**
- `contain: layout`：子树内部布局变化不冒泡到外部（例如长列表每一项内部的 reflow 不触发父容器重排）。
- `contain: paint`：溢出被裁剪，并形成独立的绘制层级。
- `contain: size`：子内容不参与父尺寸计算（必须显式给宽高），这是 `content-visibility: auto` 能跳过渲染的前提。
- `contain: content` ≈ `layout` + `paint` + `style`，是日常最常用的组合。

**边界与误区**
- `contain: size` 若忘记设置显式尺寸，元素会塌缩为 0。
- `contain` 不是银弹：对本身很简单的小盒子加 contain，反而增加合成层管理成本。
- 真正收益大的是：虚拟列表的 item、聊天气泡、瀑布流卡片、后台表格的行容器。配合 `content-visibility: auto`，首屏外的内容可以直接跳过 layout + paint。

## 🧩 3. 深度面试题：实现一个带并发上限的异步任务调度器

**题干**
实现 `class Scheduler { constructor(limit) {}; add(task): Promise }`，其中 `task` 是一个返回 `Promise` 的函数。要求同时执行的 task 不超过 `limit` 个，`add` 返回的 Promise 要在该 task 完成时 resolve 为其结果。

**追问 1**：如果某个 task reject 了，如何保证后续任务不被阻塞，且 `add` 返回的 Promise 正确 reject？
**追问 2**：如何支持「取消」—— 调用 `cancel(token)` 后，还没开始执行的任务应直接以 `AbortError` reject？
**追问 3**：如果 `limit` 是动态可调的（运行中变大/变小），实现要怎么改？变小时正在执行的任务是否要中断？

**参考答案**
```js
class Scheduler {
  constructor(limit = 2) {
    this.limit = limit;
    this.running = 0;
    this.queue = []; // { task, resolve, reject, signal }
  }

  add(task, { signal } = {}) {
    return new Promise((resolve, reject) => {
      const job = { task, resolve, reject, signal };
      if (signal) {
        signal.addEventListener('abort', () => {
          const i = this.queue.indexOf(job);
          if (i >= 0) {
            this.queue.splice(i, 1);
            reject(signal.reason ?? new DOMException('Aborted', 'AbortError'));
          }
        });
      }
      this.queue.push(job);
      this._schedule();
    });
  }

  setLimit(n) { this.limit = n; this._schedule(); }

  _schedule() {
    while (this.running < this.limit && this.queue.length) {
      const job = this.queue.shift();
      if (job.signal?.aborted) {
        job.reject(job.signal.reason);
        continue;
      }
      this.running++;
      Promise.resolve()
        .then(job.task)
        .then(job.resolve, job.reject)
        .finally(() => { this.running--; this._schedule(); });
    }
  }
}
```

**考察点**
- 并发控制的正确边界（`running < limit` 的判定时机）。
- Promise 错误传播与 `finally` 的原子性。
- `AbortController` 的生态与 `DOMException('AbortError')` 的约定。
- 面试官真正想看：你是否能区分「排队中」和「执行中」两种状态下取消的语义差异。

## 🛠️ 4. 新 API 速览：`Promise.withResolvers()`（ES2024）

**是什么**
一个在 ES2024 落地的静态方法，返回 `{ promise, resolve, reject }` 三件套，省去手动在构造器里把 `resolve/reject` 泄露到外层的「Deferred 模式」样板代码。

**解决什么问题**
把「Promise 的创建」和「Promise 的 settle 时机」解耦。典型场景：事件回调、WebSocket onopen、worker postMessage ack —— 这些你需要「先发出 promise，等外部某个事件再 resolve」。

**对比**

| 方案 | 代码量 | 作用域泄露 | 可读性 |
| --- | --- | --- | --- |
| 构造器 + 外层变量 | 中 | 需要在闭包里暴露 resolve | 一般 |
| 自写 `createDeferred` 工具 | 低 | 封装一层 | 好但需引入工具 |
| `Promise.withResolvers()` | 最低 | 无 | 原生、最佳 |

**现阶段建议：立刻学。**
Node 22、Chrome 119、Safari 17.4 及以上原生可用（部分版本号待验证）。不需要构建配置、无额外成本，是「写一次就回不去」的那种 API。

## 📂 5. 源码阅读推荐：`mitt`（约 40 行的事件总线）

**仓库 / 关键文件**：`developit/mitt`，核心文件 `src/index.ts`。

**核心思路（自己的话）**
mitt 用一个 `Map<EventType, Handler[]>` 维护订阅表。`on` 向数组 push 回调，`off` 从数组中 `splice`，`emit` 遍历数组同步调用，并对「`*` 通配订阅者」额外做一轮分发。全部不到 40 行，没有 this 绑定，没有继承，没有内存泄漏陷阱 —— 它展示了「API 极简 + 数据结构极简 + 不做防御性设计」能走多远。

**阅读切入点问题**
1. `emit` 在遍历 handlers 时使用了 `slice()` 的拷贝吗？如果没有，`off` 在回调内部调用会不会跳过下一个订阅者？
2. 为什么它选择 `Map` 而不是普通对象？—— 结合「key 可以是 Symbol / 数字 / 字符串」思考。
3. 对比 Node 的 `EventEmitter`，mitt 为什么敢不实现 `once`、`setMaxListeners`、`error` 事件？这背后反映了什么使用场景取舍？

**目标**：用 `Promise.withResolvers()`（联动板块 4）给第 3 题的 `Scheduler` 补一个 `drain()` 方法 —— 返回一个 Promise，在队列和执行中任务全部结束时 resolve。

**产出可验证**：
```js
const s = new Scheduler(2);
s.add(() => sleep(300));
s.add(() => sleep(100));
s.add(() => sleep(200));
await s.drain(); // 期望：三个任务全部完成后才继续
console.log('all done'); // 必须且只打印一次
```

**提示**：
- 在 `_schedule` 执行完毕时检查 `running === 0 && queue.length === 0`。
- `drain` 第一次调用时用 `Promise.withResolvers()` 创建 pending 的 promise，保存 `resolve`；条件满足时触发并清空。
- 边界：调用 `drain()` 时队列已空且无执行中任务，应立即返回已 resolved 的 promise。
