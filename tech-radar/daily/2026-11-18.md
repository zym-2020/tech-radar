## 🔥 1. 今日技术热点：TypeScript "Native Port"（Go 重写版）进入可试用阶段

**是什么**
微软将 TypeScript 编译器用 Go 重新实现，目标是把 `tsc`、Language Service、`--watch` 全链路提速约 10 倍（官方口径，具体版本号与达成度待验证）。目前在 `typescript-go` / `tsc-native` 相关预览通道可试，预计并入主线仓库时会与 7.x 大版本一同发布。

**解决的旧痛点**
- 大型 monorepo 的冷启动 `tsc --build` 动辄几十秒到几分钟，开发等待和 CI 时间两头受损。
- VS Code 的 TS Server 在超大项目里经常"卡菜单"，根因是单线程 JS + 巨大的 AST/Type 关系图。
- `--incremental` 的 `.tsbuildinfo` 虽然能缓存，但失效粒度粗，常常"小改动触发大重算"。

**底层原理 / 关键设计**
- 用 Go 的协程做**跨文件并行类型解析**；原 TS 实现是单线程回环（Parser → Binder → Checker）。
- Type Relations 的缓存改成**结构化指纹 + 分片**，减少失效传播。
- Language Service 走 LSP 协议进程外运行，与编辑器 UI 线程彻底解耦；编辑器只做增量请求。
- 语义严格保持与 TS 旧实现**字节级兼容**（同一份测试套件），不是"类 TS"方言（这是它和 swc/esbuild 的 TS 转译的本质区别——那俩只擦除类型、不做类型检查）。

**对日常工作的影响**
- CI 的 `tsc --noEmit` 耗时有望显著下降，释放的时间可以上更严格的规则（如 `exactOptionalPropertyTypes`）。
- 大仓切分成 project references 的收益会减弱，架构决策可以更关注"模块边界清晰度"而非"类型检查耗时"。
- 需要观望：**插件生态**（ts-patch、type-fest 复杂类型、tRPC 的类型推导）在新实现上的稳定性。生产项目**先在 CI 上并行验证**，别急着替换本地开发环境。

## 📘 2. 一个值得掌握的概念：INP（Interaction to Next Paint）的测量与归因

**是什么**
INP 是 2024 年从 FID 接棒的 Core Web Vitals 指标：测量**页面生命周期内所有交互**（点击、键按下、tap）中，从用户输入到下一帧完成绘制的最长那次延迟。阈值：≤ 200ms 良好、> 500ms 差。

**为什么需要**
FID 只测首次输入的"排队时间"，拿不到 handler 本身的执行开销和渲染开销，大量真实卡顿被漏测。INP 测的是**端到端**时长，和用户感知的"点一下卡一下"高度对齐。

**怎么实现（测量链路）**
一次交互分三段时间：
1. **Input delay**：事件进入队列到 handler 开始跑的时间——被 Long Task 挤占。
2. **Processing time**：handler 里 JS 执行时间（含 `click` / `keydown` 的同步 + 微任务）。
3. **Presentation delay**：从 handler 结束到浏览器真的 paint 完成的时间——大的 style/layout 变更会拖慢这一段。

浏览器用 PerformanceObserver 的 `event` 和 `first-input` entryType 记录各段，取整个会话里"持续时间"的 Top 2%（p98）作为该页面的 INP 分。

**边界与误区**
- 微任务链（`.then().then()...`）会被计入 processing time，这是"微任务批量更新"看似优雅、实则有坑的地方。
- `setTimeout(fn, 0)` 让渲染先跑，能把 handler 分段，但会让"用户点下去到看到反馈"更慢——不要为了压 INP 乱用。
- 使用 `scheduler.yield()`（下方 4 板块）才是正解：让出控制权但保留优先级。
- 开发工具：Chrome DevTools → Performance → Interactions 轨道，能直接看到每次交互的三段时间。

## 🧩 3. 深度面试题：实现一个带 TTL 与命中率统计的 LRU Cache

**题干**
实现 `class LRUCache<K, V>`，满足：
```ts
const c = new LRUCache<string, number>({ max: 3, ttl: 1000 })
c.set('a', 1); c.set('b', 2); c.set('c', 3)
c.get('a')            // 1，a 变成最近使用
c.set('d', 4)         // 淘汰 b
c.stats()             // { hits: 1, misses: 0, size: 3, hitRate: 1 }
await sleep(1100)
c.get('a')            // undefined（TTL 过期）
```
要求：`get`/`set` 均为 **O(1)**。

**追问 1**：为什么 Map 自己就能做到 O(1) 的 LRU？解释背后的数据结构保证。
**追问 2**：如果让 TTL 精确到"过期瞬间自动清理"（不是懒删除），该怎么设计？定时器的开销如何控制？
**追问 3**：高并发场景（Web Worker 多线程、或 SSR 多请求共享），命中率统计可能出现竞态，如何在不加锁的前提下保证最终一致？

**参考答案**
```ts
class LRUCache<K, V> {
  private max: number
  private ttl: number
  private store = new Map<K, { v: V; exp: number }>()
  private hits = 0
  private misses = 0

  constructor(opts: { max: number; ttl?: number }) {
    this.max = opts.max
    this.ttl = opts.ttl ?? Infinity
  }

  get(key: K): V | undefined {
    const entry = this.store.get(key)
    if (!entry) { this.misses++; return undefined }
    if (entry.exp < Date.now()) {         // 懒删除
      this.store.delete(key); this.misses++; return undefined
    }
    // 关键：删了再 set，Map 迭代顺序 = 插入顺序 = 最近使用顺序
    this.store.delete(key); this.store.set(key, entry)
    this.hits++
    return entry.v
  }

  set(key: K, value: V) {
    if (this.store.has(key)) this.store.delete(key)
    else if (this.store.size >= this.max) {
      // 第一个 key 就是最久未用
      const oldest = this.store.keys().next().value
      this.store.delete(oldest!)
    }
    this.store.set(key, { v: value, exp: Date.now() + this.ttl })
  }

  stats() {
    const total = this.hits + this.misses
    return { hits: this.hits, misses: this.misses, size: this.store.size,
             hitRate: total ? this.hits / total : 0 }
  }
}
```

**考察点**：`Map` 保留插入顺序（ES2015 规范）、O(1) 的双向链表等价实现、懒删除 vs 立即清理的权衡、多线程下用原子计数器（如 `Atomics.add` on `SharedArrayBuffer`）做无锁计数、数据结构选型的"规范兜底"思维。

## 🛠️ 4. 新工具/规范/API 速览：`scheduler.postTask()` 与 `scheduler.yield()`

**是什么**
W3C 的 Scheduling API 把任务优先级从"黑盒的 Task Queue"暴露给开发者。`scheduler.postTask(fn, { priority })` 支持三档：`user-blocking`（最高）、`user-visible`（默认）、`background`。`scheduler.yield()` 返回 Promise，让出当前任务但保留原优先级（Chromium 稳定，Safari/Firefox 跟进中，版本待验证）。

**解决什么问题**
`setTimeout(fn, 0)` 和 `requestIdleCallback` 都有短板：前者没有优先级，混在普通任务队列里；后者在"页面繁忙"时根本不会被调用。真正的"长任务切片 + 保持响应"过去只能靠手写 Scheduler，现在浏览器原生支持。

**和已有方案对比**

| 能力 | setTimeout(0) | requestIdleCallback | postMessage trick | **scheduler.postTask** |
| --- | --- | --- | --- | --- |
| 优先级 | 无 | 最低 | 无 | **3 档可控** |
| 最小延迟 | 4ms+（嵌套） | 不定 | ~0ms | ~0ms |
| 可取消 | clearTimeout | cancelIdleCallback | 否 | AbortSignal |
| 延迟预算 | 无 | 50ms deadline | 无 | 规范定义优先级语义 |
| 兼容性 | 全 | 良 | 全 | Chromium 稳定（待验证） |

**现阶段建议**：**立刻学，渐进增强**。写法：
```js
async function heavyWork(items) {
  for (const x of items) {
    processOne(x)
    if (navigator.scheduling?.isInputPending?.() || performance.now() % 50 < 1) {
      await scheduler.yield()  // 把控制权让给用户输入
    }
  }
}
```
不支持的浏览器用 `await new Promise(r => setTimeout(r, 0))` 兜底。

**核心思路（自己的话）**
Redux 的本体是一个发布订阅容器 + 纯函数 reducer：`createStore(reducer, preloadedState)` 返回 `{ getState, dispatch, subscribe, replaceReducer }`。`dispatch(action)` 做的三件事是：加锁（`isDispatching` 标志防止 reducer 里 dispatch）→ 用 reducer 把当前 state 推进到下一状态 → 快照一份 listeners 并全部通知。中间件通过 `applyMiddleware` 包装 `dispatch` 形成洋葱圈，这就是 redux-thunk / redux-saga 的根基。

**目标**：把第 3 题的 LRUCache 敲到一个 `lru.test.mjs`，并对比"用它缓存一个耗时函数"与"直接每次计算"的 INP 表现：
```js
import { LRUCache } from './lru.mjs'
const cache = new LRUCache({ max: 100, ttl: 5000 })

function expensive(n) { // 模拟 20ms 的计算
  const start = performance.now()
  while (performance.now() - start < 20) {}
  return n * n
}
function cached(n) {
  const hit = cache.get(String(n))
  if (hit !== undefined) return hit
  const v = expensive(n)
  cache.set(String(n), v)
  return v
}
// 在 click handler 里循环调用 cached(Math.random()*5|0) 100 次
// 打开 DevTools Performance 面板记录一次点击，看 Interaction duration
```

**产出可验证**：无缓存版的交互时长应接近 2000ms（100 × 20ms），缓存版第二次点击应 < 50ms。打开 Performance → Interactions 轨道能直接读出 INP 三段时间，印证第 2 板块的理论。

**联动**：如果想把"首次填充缓存那次慢点击"也救回来，把 `expensive` 的循环改成 `await scheduler.yield()` 切片（第 4 板块），你会看到 Input delay 显著下降，但总 processing time 变长——这正是 INP 调优里"响应感"与"总耗时"的典型权衡。
